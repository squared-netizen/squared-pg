### 2.9.1 What a kit is

A kit is the bridge layer. It connects Squared to an external system, and that
system to the platform:

```text
Squared Application
        v
Squared Framework
        v
Kit  (bridge)
        v
External Framework   (SDL3, SFML, ncurses)
        v
Platform             (Android, Linux, terminal)
```

This is the chain described in the project vision: Squared talks to SDL3 through
a bridge, and SDL3 to Android.

A kit MAY provide adapters, framework bridges, platform integration,
initialization and lifecycle code, event/input/rendering translation, build
configuration fragments, dependency declarations, platform-specific sources, kit
resources, and compatibility metadata.

A kit MUST integrate through documented Squared public interfaces and MUST NOT
modify Squared framework internals. A kit MUST NOT define the overall project
structure — that is the template's role — and MUST NOT assume it owns the
workspace.

The external framework itself remains an external dependency, conceptually
distinct from the kit that bridges it.

### 2.9.2 Kit manifest block

```json
"kit": {
  "external": {
    "id": "sdl3",
    "version": ">=3.0",
    "acquisition": "package",
    "package": "package.thirdparty.sdl3"
  },

  "provides": ["graphics", "input", "windowing"],

  "supported_templates": ["template.android.cpp", "template.terminal"],
  "supported_platforms": ["android", "linux", "desktop"],
  "supported_framework":  "^1.0",

  "requires_packages": ["package.squared.graphics"],
  "conflicts_with":    ["kit.sfml"],

  "writes_integration_points": [
    "squared.init",
    "build.targets"
  ],

  "files": [
    { "path": "sq_app/src/squared/kit_sdl3.cpp", "class": "generated" },
    { "path": "cmake/kit_sdl3.cmake",            "class": "generated" }
  ],

  "migrations": [
    { "from": "^1.0", "to": "2.0.0", "rules": "migrations/1-to-2.json" }
  ]
}
```

### 2.9.3 Integration points

An **integration point** is a named anchor a template declares
([[2.8 Templates]] §2.8.6) that kits and packages may contribute to. Points are
named, not positional, so contributions are comparable without inspecting file
content.

Rules:

- A kit MUST declare every integration point it writes.
- A kit MUST NOT write to a point the active template does not declare.
- Two kits writing the same point MUST both declare it; whether that is a
  conflict is determined by the point's declared arity.

Point arity, declared by the template:

| Arity | Meaning |
|---|---|
| `single` | exactly one contributor; a second is a conflict |
| `multi` | many contributors; contributions are emitted in resolution order |

Conflicts MUST be detected during cross-validation, **before** any workspace
mutation, and reported as a structured compatibility error. Lua then removes a
kit, selects an alternative, amends the workflow, or terminates.

`conflicts_with` declares a known incompatibility independent of integration
points, and MUST be honoured even if no point collides.

### 2.9.4 External framework acquisition

`external.acquisition` declares how the external framework reaches the generated
project:

| Value | Meaning |
|---|---|
| `package` | supplied by a named generator package (offline) |
| `system` | expected to be present on the build host |
| `vendored` | vendored into the generated project by the kit |

A kit using `system` MUST declare the detection mechanism the generated build
will use, so the generated project can find the dependency without the generator.

Offline generation MUST be possible for every kit whose `acquisition` is
`package` or `vendored`. A `system` kit MAY require host software at build time,
but MUST NOT require network access at generation time.

### 2.9.5 Dependencies

Kits MAY depend on packages, other kits, and platform components. All dependencies
MUST be declared in the manifest and MUST NOT be discovered through filesystem
convention.

The engine MUST validate the complete kit dependency graph before application.
The graph MUST be acyclic.

### 2.9.6 Composition

Multiple kits MAY be applied where compatibility permits:

```text
template.android.cpp
    +-- kit.android
    +-- kit.sdl3
```

Composition MUST be deterministic. Application order is the resolution order of
the kit set, which is itself deterministic
([[2.8 Templates]] §2.8.2).

### 2.9.7 Ownership and updates

Kit-contributed paths declare an ownership class exactly as template paths do
([[2.7 Project generation model]] §2.7.10). The generator MUST NOT overwrite a
user-authored file merely because a kit originally provided a file at that path.

Kit versions MUST be recorded in workspace metadata. A kit update MUST NOT
silently alter an existing project; updates occur only through the explicit
workflow in §2.7.11.

Where a version change requires more than file replacement — moved paths, renamed
targets, changed configuration — the kit MUST declare `migrations`. A required
migration that is unavailable MUST fail the update rather than proceeding
partially.

### 2.9.8 Validation

Before application a kit MUST be validated for: envelope and type block
correctness, template compatibility, framework version compatibility, package
requirements, platform requirements, dependency availability, integration point
declarations, conflict declarations, and required parameters.

An invalid kit MUST NOT partially modify the workspace.

### 2.9.9 Reference kit set

```text
kit.sdl3       SDL3 graphics, input, windowing
kit.sfml       SFML integration
kit.ncurses    terminal UI integration
kit.android    Android platform bridge
```
