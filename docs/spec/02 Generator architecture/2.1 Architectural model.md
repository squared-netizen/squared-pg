# 2.1 Architectural model

> [!info] Navigation

## Purpose

Establishes the fundamental architecture: a native C++ engine providing
capabilities, a Lua control layer providing orchestration, and the boundary
between the generator and the projects it generates.

## Content

### 2.1.1 The model

`squared-pg` is a native C++20 engine with a programmable Lua 5.4 control layer.

The architecture separates **capability** from **orchestration**:

- The engine provides the native capabilities required to create, manage,
  validate, and modify Squared projects.
- The Lua layer provides workflow orchestration, user interaction, command
  processing, and generation policy.
- The CLI is one consumer of that stack, not the defining interface.

The design intent is that the engine behaves like a programmable pipeline: the
engine exposes a control surface of discrete operations, and Lua sequences them.
The analogy to a graphics pipeline is deliberate — fixed capability, programmable
sequencing.

`squared-pg` MUST be usable as:

- a standalone command-line project generator;
- an embedded generation library;
- an automation component inside larger development tools;
- a programmable project-generation framework.

### 2.1.2 Engine role

The engine is the native domain layer.

The engine MUST understand the core Squared project model: `SquaredProject`,
templates, kits, packages, assets, project configuration, generated project
metadata, and resource resolution. These are domain concepts, not workflow logic.

The engine is responsible for project model representation, resource management,
filesystem operations, template processing, kit processing, package resolution,
asset handling, project validation, transactional generation, metadata
processing, and dependency resolution primitives.

The engine MUST expose these through a documented public control surface.

The engine MUST NOT contain command-line parsing, interactive prompts,
user-specific generation workflows, hardcoded assumptions about a single project
type, or hidden machine-specific paths.

The engine provides the mechanisms required to perform generation. It does not
decide the user's generation strategy.

### 2.1.3 Lua role

Lua is the programmable orchestration layer. It controls the sequence and policy
of generator operations.

Lua is responsible for command-line argument handling, standard I/O and stream
processing, configuration loading, workflow selection, user-defined generation
logic, engine API invocation, and custom workflows.

Lua determines which template is selected, which kit is applied, which packages
are included, which assets are materialized, which steps execute, and in what
order.

Lua does not replace engine functionality. It composes engine capabilities into
workflows.

### 2.1.4 Capability and orchestration

The engine provides capabilities:

```text
create_project()
resolve_template()
apply_kit()
resolve_package()
copy_asset()
validate_project()
commit_generation()
```

Lua provides orchestration:

```text
read user arguments
select the android-c++ workflow
resolve template.android.cpp
apply kit.sdl3
add package.squared.gui
resolve assets
generate project
```

The same engine capability MUST be usable from multiple Lua workflows. The same
Lua workflow SHOULD be executable from different input sources: command-line
arguments, configuration files, streams, or embedded tool input.

### 2.1.5 The control surface

The engine public API is the stable control surface exposed to Lua and to other
consumers.

It MUST expose explicit operations, use documented data models, provide
deterministic behaviour, define ownership and lifetime rules, provide structured
error reporting, and avoid hidden global state.

It SHOULD be designed around domain objects — projects, templates, kits,
packages, assets, configurations — rather than around generator internals.

### 2.1.5a How a host locates its installation

A host MUST locate its installation **by marker, never by directory name**.

The marker is a directory containing **both** `lua/workflows` and `resources`.
Both, not either: `lua/` alone matches any Lua project, and `resources/` alone
matches most things.

Search order:

1. `<prefix>/share/squared-pg`, where `<prefix>` is the executable's
   grandparent. An installed layout puts the binary in `<prefix>/bin`, and no
   amount of walking upward from there would find a sibling `share/`.
2. Walking upward from the executable, testing each ancestor for both markers.

This is what makes one binary work from a build tree, from an installed
prefix, and from `~/sqsysroot/.sqpg/bin` with no configuration and no
environment variable. The layout is the mechanism.

**The failure it replaced:** an earlier host recognised its root by the
directory names `build` and `bin`. That broke for every project with a `build`
directory of its own, which is nearly all of them, and it broke silently — the
host found *a* root, just not its own.

A host MUST NOT read an environment variable to find its installation. The
installation is where the binary is; anything else is ambient state, and
§2.7.2's prohibition exists because ambient state makes a failure depend on
who is running the tool rather than on what they asked for.

### 2.1.6 Consumers

> [!note] Resolution of Q-01 (D-025)
> The **C++ public API is the architectural boundary**. Lua is its first and
> primary consumer, but not a privileged one.

Permitted consumers of the engine:

- the Lua control layer, through the binding layer;
- an embedding application calling the C++ API directly;
- an embedding application hosting the Lua layer and supplying its own workflows.

The CLI is a thin host: it creates an engine, hands control to a Lua workflow,
forwards I/O, and reports results. **The CLI MUST NOT implement generation policy
in native code.** Generation policy belongs to Lua; generation capability belongs
to the engine.

The engine MUST NOT behave differently based on which consumer invoked it
(see [[2.16 Architectural invariants]]).

### 2.1.7 Configuration-driven generation

Generation SHOULD be configuration-driven. Configuration may arrive from
command-line arguments, configuration files, Lua scripts, programmatic API calls,
or streams.

Configuration describes the desired project state. Lua interprets it and
determines workflow execution. The engine performs the requested operations.

Supporting a new workflow MUST NOT require modifying the C++ engine.

### 2.1.8 Generator and generated-project boundary

`squared-pg` owns generation logic, templates, kits, packages, generator
resources, and workflow scripts.

Generated projects own application source code, user modifications,
project-specific assets, and application configuration.

Generated projects MUST NOT depend on `squared-pg` internals. Changes inside a
generated project MUST NOT modify the generator. The generator creates and manages
projects; it does not become part of the generated application's runtime
architecture. See [[2.12 Generated-project boundary]].

### 2.1.9 Architectural invariant

```text
                 Lua
        (workflow / orchestration)
                 |
                 v
        squared-pg Engine
        (domain capabilities)
                 |
        +--------+--------+
        |        |        |
   Templates   Kits   Packages
        |
      Assets
        |
        v
 Generated Project
```

The dependency direction MUST remain explicit, testable, and acyclic. The engine
defines generation capabilities; Lua defines how they are composed; the generated
project is the output of the system, never a dependency of it.
