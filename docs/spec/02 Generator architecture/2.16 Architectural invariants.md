## Content

### 2.16.1 The four that outrank the rest

If a change forces a choice, these win:

1. **User work is never destroyed.** ([[2.12 Generated-project boundary]])
2. **Generated projects do not depend on the generator.**
   ([[2.12 Generated-project boundary]])
3. **The engine provides capability; Lua provides orchestration.**
   ([[2.1 Architectural model]])
4. **Everything works offline from a clean checkout.**
   ([[1.13 Repository invariant]])

Everything else is a means to these.

### 2.16.2 Invariant register

| I-02 | The engine never decides workflow policy | [[2.2 Engine responsibility and role]] | no engine symbol names a template, kit, or workflow; audited by grep over the public API |

| I-08 | Generation is offline | [[1.13 Repository invariant]] | full generation suite in a network-isolated environment |

### 2.16.3 On detection

An invariant with no detection mechanism is documentation, not a guarantee. Every
row above names one; where the mechanism is weak, that is visible rather than
hidden.

This register is the resolution of open question Q-25 ([[Spec open questions]]),
recorded as [[Spec decisions#D-028 — Invariant register names a detection mechanism per invariant|D-028]].

I-10 is the weakest and deserves attention: "no undocumented global state" is only
partially checkable. The two-instance test catches state that affects results;
`clang-tidy`'s check on namespace-scope mutables catches the obvious form. Neither
catches state hidden behind a function-local static. This is a known gap.

### 2.16.4 Changing an invariant

An invariant may be changed, but not quietly. Changing one requires a decision
entry in [[Spec decisions]] recording what is given up and why, and an update to
every section that relied on it.
