## Purpose

Defines how failures are detected, classified, and reported, and the transaction
mechanics that make "leave the workspace unchanged" a guarantee rather than an
intention.

## Content

### Part 1 — Errors

### 2.15.1 Error structure

> [!note] Resolution of Q-17 (D-017)
> Two identifier fields: a coarse `category` for control flow, and a stable
> dotted `code` for diagnosis and documentation.

```text
EngineError {
    category      closed enum, for branching
    code          stable dotted string, for diagnosis
    message       human-readable, not for parsing
    operation     operation identity that failed
    resource      affected resource identity, when applicable
    path          affected workspace path, when applicable
    diagnostics   structured detail
    recovery      recovery information when available
}
```

`category` is closed so a workflow can exhaustively switch on it. `code` is open
within its category so new specific failures can be added without a breaking
change.

### 2.15.2 Categories

```text
configuration   validation   resource       template
kit             package      asset          framework
filesystem      transaction  compatibility  capability
lifecycle       internal
```

`internal` means a defect in the engine. It MUST NOT be used for any failure the
user could have caused, because a user cannot act on it.

### 2.15.3 Codes

Codes are `<category>.<subject>.<condition>`:

```text
template.not_found
template.parameter.missing
template.parameter.invalid
kit.integration_point.conflict
kit.compatibility.template
package.version.unsatisfiable
package.dependency.cycle
package.resolution.exhausted
asset.integrity
asset.transform.unavailable
filesystem.permission
filesystem.space
transaction.rollback_failed
transaction.journal.incomplete
capability.unsatisfied
lifecycle.invalid_state
```

Every code MUST be documented in `docs/programmer/`. A code is part of the public
contract: workflows branch on codes, so removing or repurposing one is a breaking
change.

Example:

```text
category:  package
code:      package.version.unsatisfiable
operation: package.resolve
resource:  package.squared.gui
message:   no version of package.squared.gui satisfies all constraints
diagnostics:
  constraints:
    - "^1.0"  required by template.android.cpp
    - ">=2.0" required by kit.sdl3
  considered: [1.4.2, 1.3.0, 1.0.0]
```

That diagnostic is actionable. "No compatible version found" is not.

### 2.15.4 Recoverable and fatal

**Recoverable** — the workflow may reasonably continue by choosing differently:
missing optional assets, unavailable optional packages, unsupported configuration
options, validation failures the user can correct. The engine SHOULD supply enough
information to choose an alternative.

**Fatal** — execution cannot safely continue: corrupted resource metadata, invalid
engine state, transaction failure, internal consistency failure. The operation
MUST fail, dependent operations MUST NOT execute, the engine MUST remain in a
defined state, and cleanup MUST remain possible.

The engine classifies. Lua decides policy: retry, alternative, report, or abort.
The engine MUST NOT enforce user-facing behaviour.

### 2.15.5 Propagation

Errors travel through the same result channel as successes
([[2.4 Engine lifecycle]] §2.4.7).

The engine MUST NOT terminate the host process, report failures only as console
output, hide failures behind partial success, or let exceptions cross the Lua
boundary. Internal exceptions MUST be converted before crossing; if conversion
itself fails, the boundary emits `internal` with the operation identity attached
([[2.6 Engine-Lua boundary]] §2.6.12).

Errors MUST be machine-readable. IDE integrations, automation, and build systems
MUST be able to determine failure without parsing human output.

### 2.15.6 Logging is not error reporting

The engine MAY provide diagnostic logging. Logs are for debugging and
troubleshooting. Results and errors are for control flow and automation. Logs MUST
NOT replace structured errors, and a workflow MUST NEVER need to read a log to
determine what happened.

### Part 2 — Transactions

### 2.15.7 Validation before mutation

The complete resource set MUST be resolved and cross-validated before the first
workspace mutation ([[2.7 Project generation model]] §2.7.9). Most failures should
therefore occur before a transaction is ever opened — the transaction system
exists for the failures that cannot be predicted, chiefly filesystem ones.

### 2.15.8 Staging strategy

> [!note] Resolution of Q-06 (D-024)
> The hardest requirement here is Termux/Android, where `/tmp` is frequently on a
> different filesystem and cross-device `rename(2)` fails. **Staging therefore
> always occurs on the target filesystem**, so cross-device rename cannot arise.

**New project generation.** Build the entire workspace in a sibling temporary
directory, then land it with one rename:

```text
<parent>/.<name>.squared-tmp/     build here
        |
        | rename()
        v
<parent>/<name>/                  atomic appearance
```

If anything fails, the temporary directory is removed and the target never
existed. This is the simple case and MUST be used whenever the target does not
yet exist.

**Regeneration.** The workspace already exists, so a single rename is not
available. Stage per file inside the workspace:

```text
<workspace>/.squared/staging/<txn>/…     new content, same filesystem
<workspace>/.squared/journal/<txn>.json  the plan of record
```

Apply by renaming each staged file into place, recording progress in the journal.

The engine MUST NOT stage in `/tmp`, `TMPDIR`, or any location not known to be on
the workspace filesystem.

### 2.15.9 The journal

The journal is a write-ahead record making an interrupted transaction
recoverable.

```json
{
  "txn": "01J8…",
  "state": "prepared",
  "workspace_metadata_version": 1,
  "operations": [
    { "op": "replace", "path": "cmake/squared_generated.cmake",
      "staged": ".squared/staging/01J8…/0001",
      "backup": ".squared/staging/01J8…/0001.bak",
      "hash_before": "…", "hash_after": "…" },
    { "op": "create",  "path": "sq_app/src/kit_sdl3.cpp",
      "staged": ".squared/staging/01J8…/0002", "hash_after": "…" },
    { "op": "delete",  "path": "cmake/kit_sfml.cmake",
      "backup": ".squared/staging/01J8…/0003.bak", "hash_before": "…" }
  ]
}
```

States:

```text
prepared  -> committing -> committed -> (journal removed)
    |            |
    |            +--> rolling_back -> rolled_back -> (journal removed)
    +--> rolling_back
```

Protocol:

1. Write every staged file. Write the journal in `prepared`. Flush the journal
   and its directory.
2. Transition to `committing` and flush.
3. Apply each operation in journal order, renaming staged content into place and
   moving replaced content to its backup path first.
4. Transition to `committed` and flush.
5. Remove staging and the journal.

A file that is replaced MUST have its previous content moved to a backup path
before the new content lands, so rollback never depends on regenerating anything.

### 2.15.10 Crash recovery

On opening a workspace the engine MUST check for a journal. If one exists, the
workspace is in an indeterminate state and the engine MUST NOT begin a new
transaction.

| Journal state | Meaning | Action |
|---|---|---|
| `prepared` | nothing applied | roll back: discard staging |
| `committing` | partially applied | resolvable either way; default is roll back using backups |
| `committed` | fully applied | complete cleanup: remove staging and journal |
| `rolling_back` | rollback interrupted | resume rollback |

Recovery MUST be idempotent — interrupting recovery and re-running it MUST reach
the same state.

The engine MUST report the recovery to the caller as a diagnostic rather than
performing it silently. A user whose generation was killed deserves to know their
workspace was repaired.

Recovery MUST NOT run automatically as a side effect of an unrelated operation
unless the caller requested it; it is an explicit operation with an explicit
result.

### 2.15.11 Durability policy

Two modes, because Termux and a CI machine want different tradeoffs:

| Mode | Behaviour |
|---|---|
| `durable` (default) | fsync staged content before rename; fsync the journal and its directory at each state transition |
| `fast` | fsync only the journal state transitions |

`fast` remains crash-*consistent* — the journal still describes what happened — but
may lose recently written content on power loss. It MUST be opt-in and MUST be
recorded in the operation result so the caller knows which was used.

### 2.15.12 Workspace locking

> [!note] Related to Q-15 (D-015)

Exactly one writer per workspace.

`<workspace>/.squared/lock` holds the process id, a start timestamp, and a
generator version. Acquisition is exclusive; the lock is released at shutdown,
including failure shutdown.

A stale lock — the recorded process no longer exists — MAY be broken, and the
break MUST be reported. A lock held by a live process MUST NOT be broken; the
operation fails with `transaction.locked`.

Read-only operations, including producing a plan, do not require the lock.

### 2.15.13 Rollback failure

Rollback can itself fail, typically on permission or space exhaustion. There must
be a defined terminal state rather than undefined behaviour.

On rollback failure the engine MUST:

- mark the journal `damaged` with the failing operation recorded;
- fail with `transaction.rollback_failed`;
- refuse further mutating operations on that workspace until the journal is
  resolved;
- leave the journal, staging content, and backups in place, since they are the
  only route to manual repair.

The engine MUST provide an operation to inspect a damaged journal and report what
was and was not applied. It MUST NOT silently delete a damaged journal — that
would destroy the user's only recovery information.

### 2.15.14 Transaction invariants

- No workspace mutation occurs outside a transaction.
- Every replaced or deleted path has a backup before the change lands.
- A failed transaction leaves the workspace unchanged or restored.
- An interrupted transaction is detectable and resolvable on next open.
- Recovery is idempotent.
- One writer per workspace.
- The engine never leaves the workspace in a state its metadata does not describe.
- Staging never crosses a filesystem boundary.
