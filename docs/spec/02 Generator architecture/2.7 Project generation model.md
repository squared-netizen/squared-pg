# 2.7 Project generation model

> [!info] Navigation
> Index: [[Specification Index]] · Parent: [[2 Generator architecture]]
> Prev: [[2.6 Engine-Lua boundary]] · Next: [[2.8 Templates]]

## Purpose

Defines how `squared-pg` transforms configuration, templates, kits, packages, and
assets into a complete, buildable, user-owned Squared project workspace — and who
owns what, when.

A generated project is not a collection of files. It is a **developer
workspace**: application code, framework integration, platform support, build
configuration, resources, and the metadata required to understand how it was
produced.

This section defines composition and ownership. Resource *definitions* — manifest
schema, identity grammar, versioning, discovery — are [[2.8 Templates]],
[[2.9 Kits]], [[2.10 Assets and generator resources]] and [[2.11 Packages]]
(D-006). The boundary *guarantee* is [[2.12 Generated-project boundary]]; the
mechanism behind it is §2.7.10 here (D-006a). Error taxonomy and transaction
mechanics are [[2.15 Error and transaction model]].

### 2.7.0 Terminology

The following terms are used with fixed meaning throughout this section.
Canonical cross-project definitions live in [[Spec glossary]]; this table fixes
the meaning of each term **within this section** and stays in sync with the
glossary (per the glossary's drift rule).

| Term | Meaning |
|---|---|
| **Workspace** | The complete generated directory tree, including all layers. Synonymous with *generated project*. |
| **Working directory** | The user working directory: the subtree the user authors code in. A subset of the workspace; see §2.7.3 (`The user working directory`). |
| **Resource** | Any generator-owned, manifest-identified unit: template, kit, package, or asset. |
| **Materialization** | Writing a resolved resource's content into the workspace. |
| **Provenance** | The recorded relationship between a generated path and the resource that produced it. |
| **Ownership class** | The regeneration policy attached to a generated path (§2.7.10). |
| **Finalization** | The commit point at which workspace ownership transfers to the user. |

`SquaredProject` refers to the engine's in-memory project model. *Squared
project* refers to the generated artifact.

### 2.7.1 Generated project definition

A generated Squared project is the primary output of `squared-pg`.

A generated project MUST be:

- **self-contained** — buildable from its own tree plus its declared external
  dependencies;
- **independent** — free of any runtime or build-time dependency on `squared-pg`
  internals;
- **reproducible** — derivable again from its recorded generation configuration;
- **legible** — understandable by a developer with no knowledge of the
  generator's implementation;
- **continuable** — suitable for ongoing development, version control, and
  relocation.

#### Project identity

Every generated project MUST have a stable project identity established at
generation time.

Project identity MUST include:

- project name;
- project type (derived from the template);
- target platform set;
- generator version;
- Squared framework version.

Project identity MUST NOT be derived from the workspace's filesystem location.
Moving a workspace MUST NOT change its identity.

#### Generator responsibility boundary

The engine performs generation capabilities. Lua selects and sequences them.

```text
Lua Workflow
    |
    | select project configuration
    v
Engine
    |
    +--> create workspace
    +--> apply template
    +--> integrate kits
    +--> resolve and materialize packages
    +--> integrate Squared framework
    +--> materialize assets
    +--> generate build configuration
    +--> validate workspace
    +--> finalize
```

The engine MUST NOT decide:

- what kind of project the user wants;
- which template is selected;
- which kits are applied;
- which packages are included;
- which assets are materialized;
- the order in which generation stages execute.

Those decisions belong to Lua or an embedding application (§2.5).

#### Relationship to the generator

```text
squared-pg
    |
    | generates
    v
Generated Squared Project
    |
    | consumes
    v
Squared Framework
```

`squared-pg` establishes the relationship between the project and the framework.
It does not participate in it. After finalization, `squared-pg` MUST NOT be
required to build, run, test, or distribute the generated project.

The single permitted exception is the update workflow defined in §2.7.11, which
is opt-in and MUST NOT be required for normal development.

### 2.7.2 Generation inputs

All generation inputs MUST be explicit.

Generation MUST NOT depend on:

- ambient environment variables;
- the current working directory;
- host-specific filesystem layout;
- interactive prompting from within the engine;
- network availability;
- the location of the generator installation.

#### Required inputs

A generation request MUST supply:

- project name;
- output workspace location;
- template identity;
- Squared framework version constraint.

#### Optional inputs

A generation request MAY supply:

- kit identities;
- package identities and version constraints;
- asset identities;
- target platform set;
- template parameters;
- package feature configuration;
- build configuration options;
- workflow-specific options.

#### Input assembly

Lua is responsible for assembling generation inputs from command-line arguments,
configuration files, streams, or an embedding application (§2.5.5, §2.5.6).

The engine receives structured configuration data and MUST validate it against
the resolved template, kit, and package contracts before any workspace mutation
occurs.

If required inputs are missing, the engine MUST return a structured validation
error identifying each missing input. The engine MUST NOT supply defaults for
identity-bearing inputs (project name, template, output location), and MUST NOT
prompt.

Lua MAY then request additional input, amend the configuration, select an
alternative workflow, or terminate.

#### Input normalization

The engine MUST normalize inputs before validation:

- resource identifiers to canonical form;
- version constraints to canonical form;
- paths to absolute form;
- platform names to the declared platform vocabulary.

Normalization MUST be deterministic and MUST NOT consult the filesystem for
anything other than path resolution.

### 2.7.3 Workspace model

#### Structural variance

The engine MUST NOT assume a single workspace layout.

Workspace structure is determined by:

- the selected template;
- the applied kits;
- the resolved packages;
- the target platform set;
- project configuration.

The template defines the workspace foundation. Kits, packages, and assets
populate declared extension points within it.

#### The user working directory

Every generated workspace MUST designate exactly one **user working directory**
— the subtree in which the user authors application code.

The generator MUST guarantee that:

- the user never needs to edit files outside the working directory to develop
  the application;
- no `generated`-class file (§2.7.10) is written inside the working directory;
- the working directory's location is declared in project metadata.

Templates MAY name this directory conventionally. The reference convention is
`sq_app/`.

#### Example layouts

`template.headless` may generate:

```text
project/
├── sq_app/
│   ├── include/
│   ├── src/
│   └── main.cpp
├── cmake/
├── CMakeLists.txt
├── .squared/
├── README.md
└── AGENTS.md
```

`template.android.cpp` may generate:

```text
project/
├── sq_app/
│   ├── include/
│   ├── src/
│   │   └── main.cpp
│   └── CMakeLists.txt
├── sq_app_android/
│   ├── AndroidManifest.xml
│   ├── assets/
│   ├── libs/
│   ├── res/
│   ├── src/
│   └── jni/
├── external/
├── cmake/
├── .squared/
├── .clang-format
├── AGENTS.md
└── README.md
```

Layouts MAY differ. The **layer model** below MUST NOT.

#### Workspace layers

A generated workspace MUST be organized into the following logical layers. A
layer MAY be a single directory, several directories, or a set of declared paths,
but each layer MUST have a declared, discoverable location.

##### Application layer

Contains user-authored code: application behaviour, game logic, user interfaces,
domain systems.

- MUST be the user working directory or contained within it.
- MUST NOT contain generator implementation detail.
- MUST NOT contain files the generator will overwrite.

##### Framework integration layer

Connects the workspace to the Squared framework and to applied kits.

MAY contain framework initialization, adapters, middleware bridges, and platform
integration code.

Generated and maintained according to template and kit rules.

##### Platform layer

Contains platform-specific project components — Android manifests and resources,
terminal launchers, desktop packaging.

MUST remain isolated from application logic where practical.

##### Build layer

Contains everything required to compile: CMake files, Gradle files, toolchain
configuration, dependency declarations.

Build files MAY be fully generated or seeded, and a seeded file MAY include a
generated fragment. The ownership class of every build file MUST be declared by
the template (§2.7.10).

##### Resource layer

Contains project resources: textures, audio, shaders, fonts, configuration,
localization data.

The workspace MUST distinguish framework resources, kit resources, and
user-authored application resources. Generator-owned resources MUST NOT silently
become user-editable application assets (§2.7.7).

#### Workspace metadata

Every generated workspace MUST contain a metadata record.

The metadata record MUST be:

- machine-readable;
- located at a declared, stable path (reference convention: `.squared/`);
- generator-owned;
- versioned.

The metadata record MUST contain:

- generator version;
- template identity and version;
- kit identities and versions;
- package identities and resolved versions;
- asset identities and versions;
- Squared framework version;
- resolved platform set;
- the normalized generation configuration;
- the working directory location;
- the layer location map;
- the file provenance table (§2.7.10).

The metadata record MAY contain a generation timestamp. It MUST NOT contain:

- absolute host paths;
- temporary filesystem locations;
- user account information;
- generator-internal state or handles.

Metadata exists to support project maintenance, reproducibility, update
workflows, and debugging. A user MUST be able to delete the metadata record and
retain a working project — losing only update capability.

#### Workspace initialization files

Templates MAY seed project documentation and development configuration:

```text
README.md
AGENTS.md
.clang-format
.clang-tidy
.editorconfig
.gitignore
```

These SHOULD establish project conventions, build instructions, development
workflow, and the generated/user ownership boundary. They are `seeded` class
(§2.7.10) unless the template declares otherwise.

#### Workspace generation rules

The generator MUST:

- create all declared directories;
- materialize all required files;
- apply selected kits at declared integration points;
- integrate resolved packages;
- resolve framework dependencies;
- record provenance for every path it creates;
- preserve declared ownership boundaries.

The generator MUST NOT:

- place generated files outside declared layer locations;
- mix generator internals into the application layer;
- require the user to understand generator implementation to build the project;
- create any dependency on the generator repository layout.

#### Workspace structure invariant

```text
User application code
        |
        v
Squared framework integration
        |
        v
Platform / middleware integration
        |
        v
Build and deployment infrastructure
```

The workspace is the developer-facing product of `squared-pg`, not an exposed
implementation detail of the generator. Its structure MUST communicate
ownership, responsibility, and extension points without reference to generator
documentation.

### 2.7.4 Template integration

The template is the first project-specific structural component applied to the
generation context. It defines **what kind of project is being created**.

```text
Lua Workflow
    | select template identity
    v
Template Service
    | resolve
    v
Template Manifest
    | validate compatibility
    v
Template Definition
    | instantiate
    v
Project Workspace
```

#### Template role

A template provides:

- workspace directory structure;
- the working directory designation;
- the layer location map;
- initial application source files;
- build system foundation;
- platform integration points;
- kit and package integration points;
- default project conventions;
- declared file ownership classes.

A template MUST be reusable across generated projects. A template MUST NOT
contain environment-specific or user-specific data.

A template MUST NOT contain generator logic. Behaviour belongs to the engine and
to Lua; templates are declarative resources.

#### Template selection

Template selection is a workflow decision.

Lua MUST determine the requested template from user input, configuration,
workflow logic, or embedding-application policy.

The engine MUST NOT select a template, MUST NOT infer one from filesystem
layout, and MUST NOT substitute an alternative when resolution fails.

#### Template resolution

The Template Service MUST resolve templates by manifest-defined resource
identity, never by path.

```text
template.android.cpp        (correct)
resources/templates/android-cpp/   (prohibited)
```

Resolution MUST verify:

- template existence;
- manifest validity;
- template version against the requested constraint;
- engine capability compatibility;
- declared dependencies;
- required parameter definitions;
- platform support for the requested platform set.

An unresolvable template MUST produce a structured error. If an alternative is
appropriate, Lua decides.

#### Template parameters

Templates MAY declare required and optional parameters — project name, package
name, namespace, application name, target platform, build configuration,
optional feature flags.

Parameters MUST be structured configuration data (§2.6.8).

Lua acquires parameters. The engine validates them against the template
contract. The engine MUST NOT obtain missing parameters by prompting; it MUST
return a structured validation error naming each missing or invalid parameter.

#### Template instantiation

Instantiation converts a resolved template into workspace structure.

Instantiation MAY:

- create directories;
- materialize template files;
- expand template variables;
- generate configuration files;
- establish the declared workspace structure;
- record initial provenance entries.

Instantiation MUST occur inside the generation transaction ([[2.15 Error and transaction model]]). Failed
instantiation MUST NOT leave a partially populated workspace visible as a
project.

#### Template processing

The engine MAY support multiple template processing strategies — direct
materialization, variable substitution, conditional file inclusion, generated
configuration, structured metadata expansion.

*Implementation note (developer docs): processors are a Strategy-pattern family
selected by manifest declaration. Adding a processor MUST NOT require changes to
the Template Service core.*

Template processing MUST be deterministic. Given equivalent template version,
parameters, engine version, and resolved resource set, instantiation MUST produce
an equivalent workspace structure and file set. Byte-identical output SHOULD be
produced where no timestamp or ordering-sensitive content is involved.

Template processing MUST NOT depend on undocumented global state.

#### Template composition

Templates MAY support composition.

Where supported:

- each composed template MUST retain its own identity and version;
- composition order MUST be deterministic and declared;
- composition MUST NOT create implicit dependencies;
- circular composition MUST be rejected with a structured error;
- the composed result MUST declare a single working directory and a single layer
  map.

```text
template.android.cpp
    +-- base application structure
    +-- Android platform structure
    +-- C++ application structure
```

Where composition is not supported by an implementation, a template MUST provide
its complete workspace foundation directly.

#### Template validation

Templates MUST be validated before any workspace mutation.

Validation SHOULD cover manifest correctness, required files, parameter
definitions, dependency declarations, engine compatibility, declared workspace
structure, processor availability, ownership class declarations, and resource
integrity.

An invalid template MUST NOT enter generation.

#### Template ownership

```text
Generator-owned template
    | instantiate
    v
Engine-owned generation state
    | finalize
    v
User-owned project workspace
```

The engine owns the runtime representation of a resolved template. The template
resource remains generator-owned. The generated workspace MUST NOT retain an
implicit runtime dependency on the template.

Template provenance MUST be recorded in project metadata (§2.7.3) so that update
workflows can identify origin explicitly rather than through hidden coupling.

### 2.7.5 Kit integration

A kit defines **how a project is integrated with an external framework,
middleware system, or platform**.

Kits are the bridge layer. They connect Squared to external systems, and those
systems to the platform:

```text
Squared Application
        v
Squared Framework
        v
Kit  (bridge)
        v
External Framework   (SDL3, SFML, ncurses, ...)
        v
Platform             (Android, Linux, desktop, terminal)
```

Examples: `kit.sdl3`, `kit.sfml`, `kit.ncurses`, `kit.android`.

A kit MUST NOT define the overall project structure. That is the template's
responsibility. A kit MUST NOT assume it owns the workspace.

#### Kit role

A kit MAY provide:

- middleware and external framework bridges;
- Squared adapters;
- platform integration;
- initialization and lifecycle code;
- event, input, and rendering translation;
- build configuration fragments;
- dependency declarations;
- platform-specific source files;
- kit resources;
- compatibility metadata.

A kit MUST integrate through documented Squared public interfaces. A kit MUST
NOT modify Squared framework internals to establish integration.

The external framework itself remains an external dependency and is
conceptually distinct from the kit that bridges it.

#### Kit selection

Kit selection is a workflow decision. Lua determines which kits are requested.

The engine MUST NOT select a kit implicitly.

Where a template declares a required kit, the workflow MAY act on that
declaration — but the act of selection remains a Lua decision, not implicit
engine behaviour.

#### Kit resolution

The Kit Service MUST resolve kits by manifest identity.

Resolution MUST validate:

- kit identity and version;
- manifest validity;
- engine capability compatibility;
- template compatibility;
- Squared framework version compatibility;
- required packages;
- platform compatibility;
- declared external framework requirements;
- declared dependencies.

An unresolvable or incompatible kit MUST produce a structured error. The engine
MUST NOT substitute an alternative kit.

#### Kit dependencies

Kits MAY depend on packages, other kits, platform components, and external
dependencies. All dependencies MUST be explicitly declared in the kit manifest.

Kit dependencies MUST NOT be discovered through filesystem convention.

The engine MUST validate the complete kit dependency graph before application.
The graph MUST be acyclic.

#### Kit composition

Multiple kits MAY be applied where compatibility permits.

```text
template.android.cpp
    +-- kit.android
    +-- kit.sdl3
```

Kit composition MUST be deterministic.

Each kit MUST declare the integration points and workspace areas it writes to.
Two kits MUST NOT write incompatibly to the same integration point. Conflicts
MUST be detected and reported as a structured compatibility error **before** any
workspace mutation.

Lua then decides: remove a kit, select an alternative, amend the workflow, or
terminate.

#### Kit application

Applying a kit MAY materialize source files, add build configuration, declare
dependencies, add platform configuration, add adapters, add resources, and
populate template-declared integration points.

Kit application MUST occur through engine services. A kit MUST NOT bypass
resource validation, filesystem controls, transaction management, ownership
rules, or compatibility checks.

Kit application MUST participate in the generation transaction whenever it
mutates the workspace.

#### Kit-owned generated content

A kit MAY contribute workspace content. The ownership class of every contributed
path MUST be declared (§2.7.10).

The generator MUST NOT overwrite a user-authored file merely because a kit
originally provided a file at that path.

#### Kit versioning

Kit versions MUST be explicit and MUST be recorded in project metadata:

```text
Project
    +-- Template: template.android.cpp@1.2.0
    +-- Kit:      kit.android@1.1.0
    +-- Kit:      kit.sdl3@1.0.3
```

A kit update MUST NOT silently alter an existing project. Updates occur only
through the explicit workflow in §2.7.11.

#### Kit failure

Kit failures MUST use the structured engine error model ([[2.15 Error and transaction model]]).

A failed kit application MUST either leave the workspace unchanged or restore it
to its prior valid state through the transaction system.

### 2.7.6 Package integration

A package defines **reusable Squared framework functionality**.

Packages are versioned, manifest-identified units of Squared functionality that
`squared-pg` can resolve and materialize into a generated project.

```text
Template  = project foundation
Kit       = external framework / platform bridge
Package   = reusable Squared functionality
Asset     = project data
```

Examples: `package.squared.core`, `package.squared.graphics`,
`package.squared.input`, `package.squared.audio`, `package.squared.gui`.

#### Package role

A package MAY provide C++ sources, public headers, libraries, build targets,
configuration, framework services, runtime resources, tests, documentation, and
package metadata.

A package MUST expose functionality through documented public interfaces. A
package MUST NOT require the generator to understand its private implementation.

A package MUST NOT redefine the architectural role of the selected template.

#### Package identity

Packages MUST have stable manifest-based identity, independent of filesystem
path, installation location, or archive name.

```text
package.squared.graphics        (correct)
resources/packages/squared/graphics/   (prohibited)
```

Lua MUST reference packages by identity.

#### Package versioning

Packages MUST be explicitly versioned. The recorded version MUST identify the
exact package interface and contents consumed by the workflow.

Where multiple versions satisfy a constraint, selection MUST be deterministic and
the selection policy MUST be documented.

The Package Service MUST reject incompatible combinations rather than silently
selecting an incompatible version.

#### Package selection

Package selection is a workflow decision. Lua determines required packages,
optional packages, package configuration, and ordering where ordering is
significant.

```lua
engine.package.resolve("package.squared.graphics")
```

The engine MUST NOT add packages based on hidden assumptions. Packages required
by a resolved template or kit MUST be declared in that resource's manifest and
surfaced to Lua, not injected silently.

#### Package resolution

Resolution MUST complete before materialization.

```text
Lua Workflow
    | request packages
    v
Package Service
    | resolve identity
    | select version
    | resolve dependency graph
    | validate compatibility
    v
Resolved Package Set
```

The Package Service MUST validate:

- package existence;
- version satisfiability;
- dependency availability;
- Squared framework compatibility;
- template compatibility;
- kit compatibility;
- platform compatibility;
- required engine capabilities;
- package integrity where applicable.

#### Package dependency model

Packages MAY depend on other packages. Dependencies MUST be explicitly declared.

```text
package.squared.gui
    +-- package.squared.graphics
    +-- package.squared.input
    +-- package.squared.core
```

The Package Service MUST resolve the complete dependency graph before any
materialization. The graph MUST be deterministic, validated ahead of mutation,
and acyclic.

Dependencies MUST NOT be inferred from filesystem contents or undocumented
convention.

Unresolvable, conflicting, or incompatible dependencies MUST produce a
structured error.

#### Package compatibility

Packages MAY declare compatibility requirements against framework version,
template, kits, platform, other packages, compiler, build system, and engine
capabilities.

```text
package.squared.android.window

requires:
    template.android.cpp
    kit.android
    squared >= 1.0
```

The engine validates. Lua decides the response: choose another package, choose
another kit, amend configuration, or terminate.

The engine MUST report incompatibility and MUST NOT alter the requested project
design to resolve it.

#### Package materialization

Materialization converts a resolved package into workspace content: sources,
headers, build definitions, configuration, runtime resources, generated
metadata.

Materialization MUST occur through engine-controlled filesystem operations. The
Package Service MUST NOT bypass the Filesystem or Transaction Services, ownership
rules, validation, or generation state management.

A failed materialization MUST NOT leave an untracked partial package in the
workspace.

Every materialized path MUST receive a provenance entry (§2.7.10).

#### Package build integration

Packages MUST supply the information required to integrate with the selected
build system: targets, compiler definitions, include directories, link
dependencies, platform flags.

```text
Application
    v
Squared::Core
    v
Squared::Graphics
    v
Platform Libraries
```

The generated project MUST contain enough information to rebuild package
integration without the generator. Developers MUST NOT need knowledge of Package
Service internals.

#### Package configuration

Packages MAY define configurable features. Configuration MUST be structured
data.

```json
{
    "package": "package.squared.graphics",
    "features": {
        "vulkan": true,
        "opengl": false
    }
}
```

Package configuration MUST NOT depend on interactive prompts, environment
variables, or generator-specific ambient state.

Lua gathers configuration. The engine validates and applies it.

#### Offline availability

Packages required for generation MUST be resolvable from declared offline
resource sources.

The Package Service MUST NOT implicitly require network access when an offline
source is declared authoritative. If a required package is unavailable offline,
the engine MUST return a structured package-resolution error.

Network-based acquisition MAY exist as an optional extension. Network access
MUST NOT become an implicit requirement of the core generator.

#### Package and kit relationship

Packages and kits are distinct concepts that MAY have declared compatibility or
dependency relationships. A kit MAY require a package; a package MAY require a
kit.

The engine MUST NOT assume every package requires a kit or that every kit
provides packages.

#### Package ownership

During generation the engine owns resolved package state, package metadata,
staging content, and transaction data.

After finalization the generated project owns materialized package files,
integrated build configuration, and generated package resources.

The package definition remains generator-owned. The generated project MUST NOT
require the original package resource to remain available, unless the project
explicitly uses an external dependency model.

#### Package failure

Package failures MUST use structured engine errors ([[2.15 Error and transaction model]]). Categories include
resolution failure, version conflict, dependency failure, compatibility failure,
and materialization failure.

A failure MUST carry enough information for Lua to determine the next action.

### 2.7.7 Asset integration

An asset defines **data consumed by the generated application**.

```text
Template  -> creates workspace
Kit       -> provides integration
Package   -> provides functionality
Asset     -> provides data
```

Assets MAY include images, textures, audio, fonts, shaders, models,
configuration data, localization files, level data, and scripts.

#### Asset identity

Assets MUST have stable resource identities, independent of storage location,
archive layout, and generator installation path.

```text
asset.texture.player        (correct)
assets/images/player.png    (prohibited as identity)
```

```text
Asset Identity -> Asset Manifest -> Physical Resource
```

An asset MUST NOT be identified only by a filesystem path.

#### Asset categories

Generated projects MUST distinguish four categories.

**Generator assets** — resources used by `squared-pg` itself (tooling data,
generator iconography). Generator assets remain generator-owned and MUST NOT
enter a generated project. Generator-internal assets MUST NOT be stored in the
project-facing asset namespace; their location is defined in [[2.10 Assets and generator resources]].

**Framework assets** — resources provided by Squared packages (default shaders,
framework fonts, runtime data). Ownership follows package ownership rules.

**Kit assets** — resources provided by integration layers (platform resources,
middleware assets, adapter resources). These remain associated with the
providing kit for the purposes of update and conflict detection.

**Application assets** — resources intended for the generated application
(textures, sound effects, UI resources, level data). These become user-owned at
finalization.

The reference `resources/assets/` namespace is an Android-style application asset
tree: it holds default application assets for generated projects and is
materialized into the platform-appropriate location by the Asset Service.

#### Asset selection

Asset selection is a workflow decision. Lua determines required assets, optional
assets, asset configuration, and placement policy.

```lua
engine.asset.resolve("asset.texture.player")
```

The engine MUST NOT include assets based on undocumented assumptions.

#### Asset resolution

Resolution MUST complete before materialization.

The Asset Service MUST validate asset existence, identity, type, integrity,
declared package requirements, transformation support, and platform
compatibility.

An invalid asset request MUST produce a structured error.

#### Asset materialization

Materialization MAY copy files, convert formats, generate metadata, create
resource indexes, and update build configuration.

Materialization MUST occur through engine-controlled filesystem operations. The
Asset Service MUST NOT bypass transaction handling, ownership rules, validation,
or the filesystem abstraction.

Every materialized asset path MUST receive a provenance entry (§2.7.10).

A failed asset operation MUST NOT leave the workspace in an undefined state.

#### Asset transformation

The Asset Service MAY transform assets: compression, format conversion,
optimization, platform packaging, metadata generation.

```text
source texture -> transformed texture -> platform resource
```

*Implementation note (developer docs): transformers are a Strategy-pattern family
keyed by asset type and target platform, resolved from the asset manifest.*

Transformations MUST be deterministic. Given identical source asset,
transformation settings, and engine version, output MUST be equivalent;
byte-identical output SHOULD be produced where the transformation is not
timestamp- or ordering-sensitive.

Transformation MUST NOT depend on hidden machine state.

#### Platform asset placement

Assets MAY require platform-specific placement.

```text
Android:  assets/  res/drawable/  res/raw/
Desktop:  resources/  data/  assets/
```

The template and applied kits determine placement rules. The Asset Service MUST
NOT assume a universal asset layout.

#### Asset and package relationship

Packages MAY declare required assets.

```text
package.squared.gui
    +-- asset.font.default
    +-- asset.texture.widgets
```

Required package assets MUST be resolved as part of package integration. The
Package Service and Asset Service MUST communicate through defined interfaces.
Packages MUST NOT manipulate asset storage directly.

#### Asset ownership and user modification

During generation the engine owns resolved asset state, transformation state,
temporary files, and staging resources.

After finalization the project owns application assets, generated resource
files, and workspace asset metadata. The generator MUST NOT retain ownership of
generated application assets.

User-modified assets MUST be protected. If an update would replace a
user-modified asset, the system MUST detect the conflict, report it, and require
explicit user action. Automatic destructive replacement MUST NOT occur
(§2.7.11).

#### Asset versioning and reproducibility

Assets SHOULD be versioned where compatibility matters, so that update workflows
can determine whether an asset is compatible, whether transformation rules
changed, and whether regeneration is required.

Asset updates MUST be explicit. The generator MUST NOT replace an asset because
a newer version exists.

Given identical asset identities, versions, transformation rules, template, kit
set, package set, and configuration, asset integration MUST produce an
equivalent asset set.

#### Asset failure

Asset failures MUST use structured engine errors ([[2.15 Error and transaction model]]). The engine reports
failure category, affected asset, diagnostics, and recovery information where
available. Lua decides the workflow response.

### 2.7.8 Squared framework integration

Squared framework integration defines how the Squared runtime, libraries,
headers, configuration, and supporting components become part of a generated
project.

The generated project MUST consume Squared through defined package and
integration interfaces.

The generated project MUST NOT depend on `squared-pg` implementation, generator
services, generator filesystem layout, or generator runtime state.

The Squared framework MUST NOT depend on `squared-pg`.

#### Framework identity

Framework version MUST be explicitly identified at generation time and MUST be
recorded in project metadata.

```text
project
    +-- Squared Framework  version: 1.0
    +-- package.squared.core
    +-- package.squared.graphics
```

The framework version MUST remain discoverable after generation, so that future
tooling can determine what was used, whether updates exist, and whether
compatibility requirements hold.

#### Framework package inclusion

Squared functionality MUST be integrated through package interfaces.

```text
Lua Workflow -> Package Selection -> Package Service
    -> Resolved Squared Components -> Generated Project
```

Framework components MUST NOT be included through undocumented filesystem
copying.

#### Framework source integration

Integration MAY occur through source inclusion, external library linking,
package-managed source trees, prebuilt libraries, or platform-specific binaries.

The integration method MUST be declared by the selected packages and project
configuration. The generator MUST NOT assume a single distribution model.

```text
Source-based:                Library-based:
project/                     project/
├── external/                ├── include/
└── squared/                 ├── libs/
    ├── include/             └── CMakeLists.txt
    └── src/
```

The generated project MUST have a clear, reproducible framework dependency
model.

#### Framework build integration

The workspace MUST contain the build configuration required to consume Squared:
targets, compiler definitions, include paths, link dependencies, platform
options, feature configuration.

```text
Application -> Squared::Core -> Squared::Graphics -> Platform Libraries
```

The generator MUST NOT require developers to manually reconstruct framework
dependencies after generation.

#### Framework initialization

Integration MAY provide startup code, service initialization, subsystem
registration, lifecycle integration, and shutdown handling.

Responsibilities MUST be separated: the application owns application behaviour
and state; the framework owns framework services, runtime state, and subsystem
management.

```cpp
int main()
{
    squared::initialize();

    Application app;
    app.run();

    squared::shutdown();
}
```

The exact initialization model depends on the selected template, kits, and
packages.

#### Framework configuration

Framework configuration MUST be structured project data and MUST remain
independent of generator implementation detail.

```json
{
    "squared": {
        "version": "1.0",
        "features": ["graphics", "input"]
    }
}
```

#### Framework resources

Framework resources (shaders, default assets, metadata, runtime data) MUST have
declared ownership and MUST NOT silently become editable application assets.

```text
Framework resources -> Application resources -> User-created assets
```

#### Framework updates

Framework updates MUST be explicit. The generator MUST NOT upgrade a framework
version during an unrelated generation operation.

Update behaviour is defined by §2.7.11.

#### Framework ownership model

```text
squared-pg owns:            generator logic, templates, kit definitions,
                            package definitions, generation services

Generated project owns:     application source, generated build system,
                            integrated framework files, project configuration

Squared framework owns:     framework implementation, runtime behaviour,
                            public APIs
```

The generated project consumes Squared. It does not become part of
`squared-pg`.

#### Framework integration invariant

```text
Template  -> provides structure
Kit       -> provides external integration
Package   -> provides Squared functionality
Generated Project -> builds and runs independently
```

Integration MUST ensure Squared remains independent from `squared-pg`, generated
projects remain independent from generator internals, framework dependencies are
explicit, framework versions are reproducible, and integration occurs through
public interfaces.

### 2.7.9 Generation phases

#### Reference phase order

A generation workflow SHOULD follow this order. Lua controls actual execution;
the engine provides the capability for each phase.

1. Acquire and normalize inputs.
2. Resolve template.
3. Resolve kits.
4. Resolve packages (including dependency graph).
5. Resolve assets.
6. Validate the complete resolved set for cross-compatibility.
7. Produce the generation plan.
8. Open the generation transaction.
9. Create the workspace.
10. Instantiate the template.
11. Apply kits.
12. Materialize packages.
13. Integrate the Squared framework.
14. Materialize assets.
15. Generate build configuration.
16. Write project metadata and provenance.
17. Validate the generated workspace.
18. Commit the transaction and finalize.

Phases 2–7 MUST NOT mutate the workspace. Phases 8–18 MUST occur inside the
transaction.

#### Resolve-before-mutate rule

The engine MUST fully resolve and cross-validate the template, kit set, package
graph, and asset set **before** the first workspace mutation.

Cross-validation MUST detect:

- template/kit incompatibility;
- kit/kit integration point conflicts;
- package dependency conflicts;
- framework version conflicts;
- platform support gaps;
- missing required parameters;
- unavailable offline resources.

A cross-validation failure MUST prevent phase 8 from beginning.

#### The generation plan

The engine MUST be able to produce a **generation plan**: the complete, ordered
set of operations and workspace paths that generation would produce, without
performing any mutation.

*Implementation note (developer docs): the plan is a reified Command list built
by a Builder over the resolved resource set. Execution consumes the same list, so
plan and apply cannot diverge.*

A plan MUST contain:

- resolved template, kit, package, asset identities and versions;
- every workspace path to be created or modified;
- the ownership class and originating resource for each path;
- required external dependencies;
- warnings and diagnostics.

The plan MUST be exposed to Lua as a structured result and MUST be available
without a workspace being created. This supports dry-run generation, update
preview (§2.7.11), testing, and tooling integration.

Executing a plan MUST produce the workspace the plan described, given an
unchanged resource environment.

#### Phase failure

Any phase MAY fail. A failure MUST:

- produce a structured error ([[2.15 Error and transaction model]]);
- prevent dependent phases from executing;
- leave the workspace unchanged or restored, via the transaction system;
- leave the engine in a valid state.

Lua determines recovery behaviour.

#### Finalization

Finalization commits the transaction and transfers ownership.

Finalization MUST:

- commit or roll back all pending workspace mutation;
- write the final metadata and provenance record;
- remove all staging and temporary state;
- produce a structured generation result.

After successful finalization the workspace is user-owned (§2.7.12).

### 2.7.10 Generated file ownership and provenance

This section defines the mechanism that makes user-file preservation and
regeneration enforceable rather than advisory.

#### Ownership classes

Every path the generator creates MUST be assigned exactly one ownership class.

| Class | Meaning | Regeneration behaviour |
|---|---|---|
| `generated` | Fully generator-managed. | MAY be overwritten. Modification is a conflict. |
| `seeded` | Created once as a starting point; user-owned thereafter. | MUST NOT be overwritten. |
| `user` | Created by the user. | MUST NOT be touched. |
| `merged` | *Reserved. Not implemented in v1 (D-020).* | — |
| `metadata` | Generator record. | Generator-managed; MAY be rewritten. |

The ownership class of every path MUST be declared by the resource that produces
it — template, kit, package, or asset manifest.

A path with no declared class MUST default to `seeded`. Defaulting to
`generated` is prohibited: the safe default is never to overwrite.

`generated`-class files MUST NOT be written inside the user working directory
(§2.7.3).

#### `merged` is reserved

> [!note] Resolution of Q-20 (D-020)
> In-place region merging is where generators corrupt user work. **v1 supports
> `generated`, `seeded`, `user` and `metadata` only.** The `merged` class name is
> reserved so that adding it later is not a breaking change.

Where a file must be both user-edited and generator-maintained — typically build
configuration — the template MUST split it:

```text
CMakeLists.txt              seeded    (user owns; includes the fragment)
cmake/squared_generated.cmake   generated (generator owns entirely)
```

A generated fragment included by a seeded file gives the generator a file it may
rewrite freely and the user a file the generator will never touch. This is
simpler and safer than marker-comment regions, and it works for every build
system the reference templates target.

#### Provenance record

The workspace metadata record MUST contain a provenance table with one entry per
generator-created path.

Each entry MUST contain:

- workspace-relative path;
- ownership class;
- originating resource identity and version;
- content hash at time of generation;
- the generation phase that produced it.

Paths MUST be workspace-relative. Absolute host paths MUST NOT appear.

Provenance is what allows the generator to distinguish "this file is unchanged
since generation" from "the user has edited this file" without guessing.

#### Conflict detection

A conflict exists when the generator would modify a path whose current content
hash does not match its recorded provenance hash.

On conflict the generator MUST:

- report the conflict as a structured result;
- identify the path, both hashes, the originating resource, and the ownership
  class;
- take no destructive action.

Lua decides the response: skip, present a diff, write alongside, request user
confirmation, or terminate.

#### Ownership rule

The generator MUST NOT overwrite user-owned content without explicit,
per-operation permission expressed through the workflow. A blanket "force" mode
MAY exist, but it MUST be explicit, MUST NOT be the default, and MUST still
report every path it overwrites.

### 2.7.11 Regeneration and update model

Regeneration is the application of generator operations to an **existing**
workspace.

Regeneration is optional. A generated project MUST remain fully usable without
ever regenerating.

#### Preconditions

Regeneration requires:

- a valid workspace metadata record;
- a valid provenance table;
- resolvable versions of the recorded resources, or explicitly requested new
  versions.

If metadata is absent or invalid, the engine MUST refuse to regenerate and MUST
return a structured error. The engine MUST NOT reconstruct provenance by
guessing from filesystem contents.

#### Operations

The update model MUST support:

- **add** — introduce a new kit, package, or asset;
- **remove** — remove a previously integrated kit, package, or asset;
- **update** — move a template, kit, package, asset, or framework version to a
  new version;
- **repair** — restore `generated`-class files to match current provenance.

Each operation is requested explicitly by Lua. The engine MUST NOT perform any
of them as a side effect of another operation.

#### Update sequence

An update MUST follow:

1. Load and validate workspace metadata and provenance.
2. Compute the current workspace state (hash every recorded path).
3. Resolve the requested target resource set.
4. Cross-validate the target set (as in §2.7.9).
5. Produce an **update plan**: paths to add, modify, remove, and paths in
   conflict.
6. Return the plan to Lua for a decision.
7. On approval, open a transaction and apply.
8. Update metadata and provenance.
9. Validate and commit.

Steps 1–6 MUST NOT mutate the workspace. The update plan MUST be obtainable as a
preview without applying it.

#### Preservation guarantees

Regeneration MUST preserve:

- all `user`-class files;
- all `seeded`-class files;
- any `generated`-class file whose hash indicates user modification, unless the
  workflow explicitly authorizes overwrite.

Regeneration MUST NOT delete a path it did not create, as recorded in
provenance.

#### Removal

Removing a kit, package, or asset MUST remove only paths whose provenance
attributes them to that resource **and** whose ownership class is `generated`
**and** whose hash is unmodified.

Paths that are user-modified, `seeded`, or `user` MUST be reported as orphaned
rather than deleted. Lua decides.

#### Version migration

A resource version change MAY require migration beyond file replacement — moved
paths, renamed targets, changed configuration schemas.

Where migration is required, the resource MUST declare migration rules. The
engine MUST apply declared migrations as part of the update transaction.

If a required migration is unavailable, the update MUST fail with a structured
compatibility error rather than proceeding partially.

#### Framework version updates

Updating the Squared framework version MAY require package updates, build
configuration changes, source changes, and metadata changes.

Framework updates MUST be explicitly requested, MUST be validated against every
resolved package and kit, and MUST follow the same plan-and-approve sequence.

#### Transaction requirement

Regeneration MUST occur within a generation transaction ([[2.15 Error and transaction model]]). A failed update
MUST restore the workspace to its pre-update state.

The engine MUST NOT leave a workspace in a state where its metadata describes a
resource set that does not match its files.

---

### 2.7.12 Ownership transition

The boundary *guarantee* — what a generated project may never contain and may
never require — is stated in [[2.12 Generated-project boundary]]. This subsection
defines only the mechanism by which ownership moves.

During generation the engine owns:

- staging directories;
- temporary files;
- transaction state;
- intermediate generated data;
- resolved resource state.

After successful finalization the user owns:

- the workspace and all its files;
- application source;
- materialized packages, assets, and integration code;
- generated build configuration;
- all subsequent modifications and build outputs.

Ownership transfer occurs at commit. It MUST be atomic with respect to the
transaction: either the workspace exists and is fully owned by the user, or it
does not exist as a valid project.

### 2.7.13 Project generation invariants

The project generation model MUST preserve the following, regardless of
implementation.

**Separation of concerns**

```text
Template  = project foundation
Kit       = external framework / platform bridge
Package   = reusable Squared functionality
Asset     = project data
```

No component may assume the role of another.

**Capability and orchestration.** The engine provides generation capabilities.
Lua selects and sequences them. The engine MUST NOT decide project type,
template, kits, packages, assets, or workflow order.

**Explicit inputs.** Every generation input MUST be explicit. Generation MUST NOT
depend on hidden machine state, ambient environment, or the current working
directory.

**Identity over paths.** All resources MUST be referenced by manifest identity.
Filesystem layout MUST remain an implementation detail of the generator and MUST
NOT appear in Lua workflows or generated project configuration.

**Resolve before mutate.** The complete resource set MUST be resolved and
cross-validated before the first workspace mutation.

**Deterministic resolution.** Given identical inputs, resource versions, and
engine version, resolution MUST produce an identical resolved set. Generated
output SHOULD be byte-identical where no timestamp- or ordering-sensitive content
is involved.

**Transactional generation.** All workspace mutation MUST occur within a
transaction. A failure MUST leave the workspace unchanged or restored. An
incomplete workspace MUST NOT be presented as a valid project.

**Declared ownership.** Every generated path MUST have a declared ownership class
and a provenance entry. The generator MUST NOT overwrite user-owned content
without explicit authorization.

**User work preservation.** Regeneration MUST preserve user-authored work.
Destructive replacement MUST require explicit action.

**Framework independence.** The Squared framework MUST NOT depend on
`squared-pg`. The generated project MUST NOT depend on `squared-pg` internals.

**Offline capability.** Generation MUST be possible from a clean repository
checkout plus declared vendored dependencies, with no network access, on a
lightweight host.

**No dependency leakage.** Nothing about the generator's implementation,
repository layout, or installation location may appear in the generated project.
