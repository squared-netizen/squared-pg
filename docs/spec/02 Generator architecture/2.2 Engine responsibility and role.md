## Content

### 2.2.1 Role

`engine/` is the native implementation layer. It exists to provide stable,
reusable, testable APIs performing the computational and filesystem-oriented work
of generation.

The engine MUST provide:

- deterministic operations;
- explicit state management;
- well-defined input/output contracts;
- reusable APIs callable from Lua bindings and from C++ directly;
- platform-independent functionality where possible.

### 2.2.2 The pipeline analogy

The engine SHOULD be structured like a programmable pipeline:

1. Engine initialization creates the generator execution environment.
2. Initialization exposes the available control surface.
3. Lua configures and sequences engine operations.
4. Engine operations execute the requested actions.
5. Results return through the Lua boundary.

This is the shape described in the project vision: fixed, well-tested capability
with programmable sequencing on top.

### 2.2.3 Domain model

The engine MUST understand the core data models required to manipulate Squared
projects:

- `SquaredProject`
- Template
- Kit
- Package
- Asset
- Configuration
- Generated project metadata

> [!note] Resolution of Q-14 (D-014)
> These are the engine's native domain model, not workflow logic. The earlier
> draft's "the engine MAY contain knowledge of Squared project domain concepts"
> is deleted; understanding the domain model is a MUST.

### 2.2.4 Engine responsibilities

The engine SHOULD contain:

- project filesystem operations;
- transactional file generation;
- template expansion;
- package and asset processing;
- archive handling;
- metadata processing;
- dependency resolution primitives;
- validation systems;
- build-configuration emission;
- resource management.

### 2.2.5 Prohibitions

The engine MUST NOT contain:

- command-line argument parsing;
- interactive prompts;
- user-specific workflow logic;
- assumptions about a single generation workflow;
- hidden filesystem paths;
- user-facing presentation policy.

The engine MUST NOT decide which template a user should select, which kit should
be applied, which packages should be included, or how a project should be
structured for a specific workflow. Those decisions belong to
[[2.5 Lua control layer]].

### 2.2.6 Capabilities, not workflows

The engine API MUST expose capabilities rather than workflows.

The engine MAY provide:

```text
create_directory()
copy_resource()
apply_template()
load_package_manifest()
validate_project()
```

Lua decides when they are called, in what order, which template is selected,
which kit is applied, and what project type is generated.

This separation is what allows `squared-pg` to serve command-line usage,
automated build tools, IDE integrations, custom generators, and third-party
tooling from one implementation.

### 2.2.7 API stability

The public C++ API MUST be documented and versioned. Changes to the control
surface MUST preserve compatibility where possible and MUST document breaking
changes where they cannot.

Public API documentation belongs in `docs/programmer/`; implementation detail
belongs in `docs/developer/` (see [[1.8 Documentation]]).
