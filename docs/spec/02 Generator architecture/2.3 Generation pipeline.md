## Purpose

project, and which side of the boundary owns each stage.

## Content

### 2.3.1 Conceptual stages

| # | Stage | Owner |
|---|---|---|
| 1 | Input acquisition | Lua |
| 2 | Configuration loading | Lua |
| 3 | Configuration validation | engine, invoked by Lua |
| 4 | Workflow selection | Lua |
| 5 | Template resolution | engine Template Service |
| 6 | Kit resolution | engine Kit Service |
| 7 | Package resolution | engine Package Service |
| 8 | Asset resolution | engine Asset Service |
| 9 | Squared framework integration | engine |
| 10 | Project generation | engine |
| 11 | Generated-project validation | engine |
| 12 | Finalization | engine |

Workflows MAY add, remove, or reorder stages provided they preserve the
architectural invariants — in particular, resolution before mutation.

```text
                 User / Tool Input
                         |
                         v
                    Lua Workflow
                         |
        +----------------+----------------+
        |                |                |
        v                v                v
  validate_config  resolve_template  resolve_kit
        |                |                |
        +----------------+----------------+
                         |
                         v
                 Engine Operations
                         |
                         v
              Generated Squared Project
```

### 2.3.2 Input acquisition

Inputs MAY originate from command-line arguments, standard input, streams,
configuration files, embedded application APIs, or automated systems.

Input acquisition belongs to Lua. The engine MUST NOT parse command-line syntax
or define interaction behaviour. Lua converts external input into structured data
for engine APIs.

### 2.3.3 Configuration loading and validation

Lua locates and loads configuration. The engine MAY provide parsing and
validation services but MUST NOT decide how configuration is obtained.

Validation SHOULD cover required fields, resource availability, template
compatibility, kit compatibility, package compatibility, platform requirements,
and dependency availability.

Invalid configuration MUST prevent generation from proceeding.

### 2.3.4 Workflow selection

Workflow selection belongs entirely to Lua. The engine MUST NOT select workflows;
it executes operations requested by the selected workflow.

### 2.3.5 Resolution stages

For each of template, kit, package, and asset resolution: Lua determines *what*
is requested; the engine determines *whether it can be resolved* and reports the
result.

The engine MUST NOT substitute an alternative resource when resolution fails. If
an alternative is appropriate, Lua selects it.

Detailed resolution semantics are defined per resource type in
[[2.8 Templates]], [[2.9 Kits]], [[2.11 Packages]] and
[[2.10 Assets and generator resources]].

### 2.3.6 Generation, validation, finalization

Lua initiates generation. The engine performs filesystem operations, template
expansion, resource materialization, file creation, and transaction management.

After generation the workflow MUST validate the generated project. The engine
provides validation capability; Lua determines validation policy and the response
to failures.

Finalization commits the transaction and transfers ownership to the user.

### 2.3.7 Transaction boundaries

Generation workflows MUST define transaction boundaries. Before modifying a
user-visible project directory the workflow MUST establish one.

On failure: incomplete output MUST NOT be presented as a valid generated project,
rollback MUST occur, and errors MUST be reported through the engine error system.

Mechanics are defined in [[2.15 Error and transaction model]]; the engine
guarantees transactional correctness for the operations it performs, and Lua
determines recovery behaviour.

### 2.3.8 Pipeline invariants

- Generated projects MUST NOT depend on `squared-pg` internals.
- Engine operations MUST be deterministic.
- Lua MUST remain responsible for orchestration.
- Engine capabilities MUST remain usable outside the CLI.
- Workflows MUST use documented engine APIs.
- The resolved resource set MUST be reproducible from equivalent inputs.
