### 2.8.1 Resource identifier grammar

> [!note] Resolution of Q-04 (D-022)

```text
identifier   = type "." segment { "." segment }
type         = "template" | "kit" | "package" | "asset"
segment      = lower { lower | digit | "-" lower | "-" digit }
lower        = "a".."z"
digit        = "0".."9"
```

Rules:

- Identifiers are lowercase. Case is significant and uppercase is invalid.
- A segment MUST start with a letter. Hyphens MAY appear inside a segment but MUST
  NOT start or end it, and MUST NOT be doubled.
- An identifier MUST have at least one segment after the type and MUST NOT exceed
  128 characters.
- Identifiers MUST be unique within their type across the active resource
  environment. A duplicate identity is an initialization failure, not a silent
  override.

`template.android.cpp` is therefore valid: type `template`, segments `android`
and `cpp`. Dots separate segments; they do not appear inside one.

Reserved namespaces:

- `package.squared.*` — first-party Squared framework packages.
- `*.squared-pg.*` — reserved for generator-internal use.

Third-party resources SHOULD use a vendor segment, for example
`kit.acme.raylib`.

#### An identity names the artifact, not the host

A resource identity MUST describe **what the resource is or produces**, never
where it happens to run or be built. Platform applicability belongs in
`platforms`, which is data a resolver can act on; an identity is a name and a
resolver cannot reason about it.

`template.termux.cpp` was renamed `template.terminal.cpp` for this reason: it
produces a terminal application, and that Termux is a convenient place to
build one is a property of the host, not of the artifact. Nothing about the
template is Termux-specific, and the name was the only thing claiming
otherwise.

`template.android.cpp` keeps its name under the same rule. Android is what it
*produces* — an APK, a NativeActivity, a specific packaging model — not where
it is built.

`kit.termux` is likewise correct: the thing it wraps is the Termux:API
toolset. A kit that wraps a platform's facilities may name that platform,
because the platform is its subject.

### 2.8.2 Version and constraint grammar

Versions are **SemVer 2.0.0**. Pre-release and build metadata are permitted;
build metadata is ignored for ordering.

A resource is referenced as `identity` or `identity@constraint`:

| Constraint | Meaning |
|---|---|
| `1.2.3` | exactly 1.2.3 |
| `^1.2.3` | `>=1.2.3 <2.0.0` |
| `~1.2.3` | `>=1.2.3 <1.3.0` |
| `>=1.2 <2.0` | explicit range |
| `*` or omitted | any available version |

Selection policy, which MUST be deterministic:

1. Collect all indexed versions of the identity.
2. Discard versions failing any accumulated constraint.
3. Sort descending by SemVer precedence.
4. Select the highest remaining version.
5. If none remain, fail with `*.version.unsatisfiable`.

Where dependency resolution requires backtracking, candidates MUST be visited in
that same descending order, so that resolution is reproducible.

Pre-release versions MUST NOT be selected unless explicitly requested by a
constraint naming a pre-release.

#### Partial operands

A range operand MAY omit trailing components. `^1.0`, `>=0.1` and `~1.2` are
all legal and pad with zeros to three components: `^1.0.0`, `>=0.1.0`,
`~1.2.0`.

A manifest's own `version` is **not** padded. An identity is exact and a
resource that cannot say which version it is has a defect, not a default.

The padding is not a convenience. Callers write:

```cpp
if (range && range->satisfied_by(candidate)) { ... }
```

so a range that fails to parse yields an empty optional and the constraint
**silently never applies** — a resource declaring `^1.0` would accept every
version in existence rather than failing to load. The failure mode of not
padding is not an error message; it is a constraint that quietly evaporates.

### 2.8.3 Manifest envelope

> [!note] Resolution of Q-03 (D-021)
> Manifests are **JSON**, in a file named `manifest.json` at the resource root,
> parsed with the vendored yyjson. JSON is already a build dependency, is fully
> offline, has an unambiguous grammar, and — unlike Lua tables — is inert data
> that can be validated statically and read safely from a sandbox.

Every resource manifest, regardless of type, MUST contain this envelope:

```json
{
  "schema_version": 1,
  "id": "template.android.cpp",
  "type": "template",
  "version": "1.0.0",
  "description": "Android C++ application workspace",

  "requires_engine": "^1.0",
  "requires_capabilities": [
    "capability.template.substitute@^1.0",
    "capability.archive.zip@^1.0"
  ],

  "dependencies": [
    { "id": "package.squared.core", "version": "^1.0", "optional": false }
  ],

  "platforms": ["android"],

  "template": { }
}
```

Envelope rules:

- `schema_version` is an integer. An engine MUST refuse a manifest whose
  `schema_version` it does not support, with a structured error.
- `id` MUST match §2.8.1 and its `type` prefix MUST equal `type`.
- `version` MUST be valid SemVer.
- `requires_engine` constrains the engine version.
- `requires_capabilities` lists engine capability tokens
  (see [[2.14 Extensibility model]]).
- `dependencies` entries are resource references; `optional` defaults to `false`.
- The type-specific block is named for the type: `template`, `kit`, `package`, or
  `asset`. Exactly one MUST be present and it MUST match `type`.
- Unknown envelope keys MUST be preserved and ignored, so newer manifests remain
  readable by older engines within the same `schema_version`.

The **Resource Service** validates the envelope: JSON well-formedness, identity
and version syntax, required keys, and integrity. The **owning typed service**
validates the type block (D-012).

### 2.8.4 Discovery and indexing

Resources are discovered by scanning declared resource roots for directories
containing `manifest.json`. Discovery produces the immutable resource index
described in [[2.4 Engine lifecycle]] §2.4.4.

Directory layout beneath a resource root is a maintainer convenience and MUST NOT
form part of any contract. A resource MUST be locatable solely through the index.

Discovery MUST be deterministic: roots are scanned in declared order, and entries
within a root in sorted order, so that duplicate-identity conflicts are reported
consistently rather than depending on filesystem enumeration order.

### 2.8.5 What a template is

A template defines **what kind of project is being created**. It provides:

- workspace directory structure;
- the working directory designation;
- the layer location map;
- initial application source files;
- build system foundation;
- kit, package, and platform integration points;
- default project conventions;
- the declared ownership class of every path it produces.

A template MUST be reusable across projects, MUST NOT contain environment- or
user-specific data, and MUST NOT contain generator logic. Templates are
declarative resources; behaviour belongs to the engine and to Lua.

### 2.8.6 Template manifest block

A template's declarations live in its cartridge manifest under
`consumers.squared_pg` (cartridge format §5.6). **This section is the only
normative definition of that schema.** The container format carries the
section as opaque text and validates nothing inside it, so no rule below is
enforced by `sqcart`.

```json
"consumers": {
  "squared_pg": {
    "project_types": ["application"],
    "working_directory": "sq_app",
    "platforms": ["all"],

    "layers": {
      "application": ["sq_app"],
      "build":       ["Makefile", "mk"]
    },

    "integration_areas": ["render.backend", "app.entry"],
    "integration_arity": { "render.backend": "single" },

    "parameters": [
      { "name": "project_name", "type": "identifier", "required": true },
      { "name": "namespace",    "type": "identifier", "required": false,
        "default_from": "project_name" }
    ],

    "processor": "substitute",
    "executable": ["run.sh"],

    "requires": {
      "engine":       ">=0.1.0 <0.2.0",
      "framework":    ">=1.0.0 <2.0.0",
      "capabilities": ["capability.project.plan@^1.0"],
      "packages":     [],
      "kits":         { "required": ["kit.terminal"], "optional": ["kit.lua"] }
    },

    "ownership": {
      "generated": ["mk/squared_generated.mk"],
      "user":      [],
      "shared":    [],
      "default":   "user"
    }
  }
}
```

#### Members

| Member | Type | Absent | Read by |
|---|---|---|---|
| `working_directory` | string | no working directory; every path is generator-visible | resolution |
| `platforms` | array of string | admits every platform | resolution |
| `layers` | object of arrays | no layer mapping | planning |
| `integration_areas` | array of string | the template offers no anchors | resolution |
| `integration_arity` | object | every area is `single` | planning |
| `parameters` | array of objects | no declared parameters | planning, validation |
| `processor` | string | `substitute` | planning |
| `executable` | array of glob | nothing is marked executable | planning |
| `requires.engine` | range | unconstrained | indexing |
| `requires.framework` | range | unconstrained | resolution |
| `requires.capabilities` | array of token | demands nothing | resolution |
| `requires.packages` | array of identity | none | validation |
| `requires.kits.required` | array of identity | none | validation |
| `requires.kits.optional` | array of identity | none | *not read* |
| `ownership` | object | every path is `seeded` | planning |
| `project_types` | array of string | — | *not read* |

#### Malformed values fall back; `processor` does not

A member whose value is of the wrong shape is treated as absent and takes the
default in the table above. It is not an error.

This is deliberate and it is the consequence of §5.6: no reader validates the
section, so a manifest can carry anything, and a generator that refused to run
over an unrecognised value would be unable to open a cartridge written for a
newer version of itself.

**`processor` is the exception.** An unrecognised processor MUST fail with
`capability.unsatisfied` rather than falling back to `substitute`. The other
members describe *what to generate*; `processor` describes *how to transform
content*, and silently substituting the wrong transform would produce a
workspace that looks correct and is not.

#### `ownership`

The three pattern lists MUST NOT overlap one another (§2.7.10). `default` is
the class taken by any path no pattern matches; where `default` is absent, an
unmatched path is `seeded`.

The manifest's vocabulary is not the engine's. `user` here means *the author
owns this file*, which the engine records as `seeded` — written once and never
rewritten. `OwnershipClass::user` describes a file the generator never writes
at all, which no manifest can enumerate. `shared` is §2.7.10's reserved
`merged` and is also recorded as `seeded` in v1 (D-020).

#### Members read by nothing

`project_types` and `requires.kits.optional` appear in every shipped template
and no code reads either.

They are recorded here rather than quietly omitted, because an author copying
a shipped manifest will copy them and be entitled to assume they do something.
They are reserved: an implementation MUST accept them and MUST NOT rely on
them. Removing them is a decision for the version that gives them meaning or
deletes them.

Rules:

- `working_directory` MUST name exactly one path (D-001). It MUST appear in the
  `application` layer. No `generated`-class path may fall inside it.
- `layers` MUST declare a location for each layer the template uses. A layer with
  no content MAY be omitted.
- `integration_points` names the anchors kits and packages may write to
  ([[2.9 Kits]]).
- `files` entries MAY use glob patterns. The most specific matching entry wins;
  where two patterns are equally specific the manifest is invalid, not resolved
  by order.
- A path matching no entry defaults to `seeded` (D-004).

### 2.8.7 Parameters

Parameters are declared with a name, a type, and whether they are required.
Parameter types are drawn from a closed vocabulary — `string`, `identifier`,
`java_package`, `path`, `bool`, `integer`, `enum` — so that validation is
performed by the engine rather than by template logic.

#### The effective parameter set

Validation is performed against the **effective** set, not against the
declared one. Three layers contribute, and every step is put-if-absent, so
precedence runs:

    workflow value  >  engine built-in  >  declared default

The layers are *applied* in the opposite order from that precedence:

1. **Workflow values.** Whatever the invocation supplied. Present first, so
   everything below can only fill gaps.
2. **Engine built-ins.** Contributed by the engine, never declared by the
   template.
3. **Declared defaults.** The template's own `default` and `default_from`,
   applied **last**.

Defaults come last so that `"default_from": "project_name"` resolves: the
built-in it references must already be present when the default is evaluated.
Applying them first — the ordering a reader would assume, and the one this
section stated before D-053 — would make every `default_from` referencing a
built-in silently produce an empty value.

The order costs nothing else. Because each step is put-if-absent, a workflow
value still wins over both, and a template default for a name the engine also
provides is redundant rather than in conflict.

#### Engine built-ins

| Name | Value |
|---|---|
| `project_name` | the requested project name |
| `namespace` | the project name, unless overridden |
| `working_directory` | the resolved working directory |
| `generator_version` | the running engine's version |
| `template_id` | the resolved template's identity |
| `template_version` | the resolved template's version |
| `framework_version` | the requested framework version, or `0.0.0` |
| `kit_list` | the resolved kit identities, comma-separated, or `none` |

Every built-in derives from the request or from the engine. **None derives
from the environment or the clock**: §2.7.2 forbids ambient inputs, and
§2.7.13 requires byte-identical output from equivalent inputs, which a
timestamp would destroy.

A template MAY declare a parameter that shares a built-in's name. Doing so has
no effect unless the built-in is absent, which for the eight above it never
is.


Lua acquires parameter values. The engine validates them against the declared
contract. The engine MUST NOT prompt; missing or invalid parameters produce a
structured validation error naming each one.

A parameter MAY declare a `default` or a `default_from` referencing another
parameter. Defaults MUST be pure derivations, never environment lookups.

### 2.8.8 Processing

A template declares a processor. The engine MAY provide several; each is an
engine capability token.

| Processor | Behaviour |
|---|---|
| `copy` | direct materialization, no substitution |
| `substitute` | variable substitution plus conditional file inclusion |

Substitution syntax is `{{ parameter_name }}`. A literal brace pair is escaped as
`{{"{{"}}`. An unknown parameter reference is an error, never an empty string —
silent substitution failure produces broken projects that look generated
correctly.

Conditional inclusion is declared in the manifest, not embedded in file content,
so that the file set is knowable before any file is read:

```json
{ "path": "sq_app_android/**", "class": "generated", "when": "platform == android" }
```

Processing MUST be deterministic and MUST NOT depend on undocumented global
state.

*Pattern: Strategy. Processors are selected by manifest declaration; adding one
requires no change to the Template Service core.*

### 2.8.9 Composition

Templates MAY support composition. Where supported:

- each composed template retains its own identity and version;
- composition order MUST be declared and deterministic;
- circular composition MUST be rejected;
- the composed result MUST declare exactly one working directory and one layer
  map;
- conflicting `files` entries between composed templates MUST be an error, not a
  silent last-wins.

Where composition is not implemented, a template MUST provide its complete
workspace foundation directly.

### 2.8.10 Validation

Before use a template MUST be validated for: envelope correctness, type block
correctness, identity and version syntax, referenced files existing, parameter
declarations well-formed, ownership classes assignable, processor availability,
declared kit and package references resolvable, layer map completeness, and
working directory validity.

An invalid template MUST NOT enter generation.

### 2.8.11 Reference template set

```text
template.headless      no I/O layer; library or service projects
template.terminal      standard I/O application
template.ncurses       TUI application
template.android.cpp   Android C++ application workspace
```

These are the templates the first release targets, drawn from the project vision.

## Open questions

- **Q-21** — is composition implemented in v1? The four reference templates share
  substantial structure, which argues for it; self-contained templates are simpler
  and cannot produce composition-order bugs. Decide when the reference templates
  are authored.
