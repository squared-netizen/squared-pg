## Purpose

Defines the contract between the native engine and the Lua control layer: the
narrow, explicit surface through which they communicate.

## Content

### 2.6.1 Boundary responsibilities

The boundary MUST define callable APIs, supported data representations, ownership
transfer rules, resource lifetime rules, result representation, error
propagation, filesystem abstraction, configuration representation, and operation
invocation rules.

The boundary MUST NOT expose internal C++ classes, internal memory ownership,
private engine state, service implementation details, filesystem implementation
details, or compiler-specific data structures.

It exists to provide controlled communication, not to expose internals.

### 2.6.2 Architecture model

```text
Lua Workflow
     |
Lua Binding Layer
     |
Engine Public API
     |
Engine Services / Operations
     |
Operation Result
     |
Lua Workflow
```

The binding layer translates between Lua representations, engine API contracts,
and native types. **The binding layer MUST NOT become a workflow layer**: it MUST
NOT select templates or kits, determine generation order, implement generation
policy, or bypass engine services.

### 2.6.3 Binding layer

The binding layer exposes approved engine APIs, converts Lua values into engine
input types, converts results into Lua values, preserves ownership rules, and
translates errors.

It MUST be generated from or validated against the operation registry
([[2.4 Engine lifecycle]] §2.4.6), so that the set of callable operations cannot
drift from the set of registered ones.

It MUST NOT implement workflows, make resource decisions, modify engine
behaviour, access private state, or bypass service boundaries.

### 2.6.4 Public API exposure

Lua accesses engine functionality only through documented public APIs.

```lua
engine.validate_configuration(config)

local template = engine.template.resolve("template.android.cpp")
local kit      = engine.kit.resolve("kit.sdl3")
local result   = engine.project.generate(project_config)
```

Lua MUST NOT access internal C++ objects, service implementation classes, private
resource managers, filesystem internals, or native memory ownership.

The public API MUST remain independent from command-line behaviour and MUST
support Lua workflows, embedded applications, IDE integrations, automated systems,
and test environments.

### 2.6.5 Data crossing the boundary

Supported representations: strings, numbers, booleans, arrays, maps, structured
configuration objects, resource identifiers, operation requests, operation
results, and diagnostic information.

The boundary MUST NOT expose raw memory addresses, unmanaged pointers, internal
object layouts, or compiler-specific structures.

Numeric care: Lua 5.4 distinguishes integers and floats. Version components,
counts, and sizes MUST cross as integers. The binding layer MUST NOT silently
narrow or coerce values; conversion loss MUST be a structured error.

Representations MUST remain stable across compatible engine versions.

### 2.6.6 Handle model

Engine objects exposed to Lua MUST use controlled references — opaque handles,
identifiers, or managed references — never raw pointers or addresses.

Handles MUST have explicit ownership and lifetime rules, become invalid after
destruction, and be validated by the engine before use. Using a stale handle MUST
produce a structured error, never undefined behaviour.

Lua MUST NOT directly manage native object lifetime.

### 2.6.7 Resource identity across the boundary

Resources cross the boundary as identities.

```lua
local template = "template.android.cpp"
local kit      = "kit.sdl3"
local package  = "package.squared.gui"
```

Lua MUST NOT reference resources by physical path.

```text
Resource Identifier
        |
        v
Resource Manifest
        |
        v
Physical Resource
```

The Lua layer MUST remain independent from repository layout. Identity grammar is
defined in [[2.8 Templates]] (D-022).

### 2.6.8 Configuration representation

Configuration crosses as structured data. Lua converts external input into
engine-compatible configuration.

```text
User Input
     |
Lua Configuration Layer
     |
Engine Configuration Validation
     |
Validated Generator State
```

The engine MUST validate configuration and MUST NOT parse user-facing command
syntax. Command-line policy belongs to Lua.

### 2.6.9 Ownership and lifetime rules

```text
Lua owns:                    Engine owns:
  workflow data                services
  configuration tables         resources and the resource index
  script state                 native objects
  user interaction state       operation state
                               transactions and staging
```

Lua MUST NOT manually destroy engine-owned resources. The engine releases native
resources according to [[2.4 Engine lifecycle]]. Temporary objects exposed to Lua
MUST have explicitly documented lifetime.

Values crossing into Lua SHOULD be copied rather than referenced where the copy
is cheap; where a reference is necessary, its validity window MUST be documented.

### 2.6.10 Operation invocation

An operation request MUST carry operation identity, required parameters, optional
parameters, and execution context where required.

```lua
local result = engine.execute({
    operation  = "project.generate",
    parameters = project_config
})
```

The engine validates operation availability, parameters, required services,
resource availability, and compatibility.

Lua determines which operations execute, in what order, under what conditions,
and how to recover. The engine determines how operations execute, how resources
are accessed, internal sequencing, and result generation.

### 2.6.11 Result representation

```text
OperationResult
    status
    data
    warnings
    diagnostics
    errors
    metadata
```

Lua MUST be able to determine whether execution succeeded, what data was
produced, what warnings occurred, what errors occurred, and whether recovery is
possible.

The representation MUST remain stable across compatible engine versions.

### 2.6.12 Error propagation

Errors cross as structured results.

The engine MUST NOT throw unmanaged exceptions into Lua, terminate the host
process, require log parsing, or hide failures behind partial success.

Internal C++ exceptions MAY exist but MUST be converted into engine error results
before crossing. If conversion itself fails, the boundary MUST produce a generic
`internal` error with the operation identity attached rather than propagating an
unknown exception — the boundary is never allowed to leak.

```lua
result.error.category
result.error.code
result.error.message
result.error.resource
```

Lua decides retry behaviour, alternate workflows, user messaging, and
termination. Categories and codes are defined in
[[2.15 Error and transaction model]].

### 2.6.13 Filesystem and path abstraction

Filesystem interaction affecting generator resources and generated workspaces
MUST be performed by the engine.

Lua MAY supply requested output locations, user workspace locations, and
configuration paths, and MAY perform user-space I/O for its own inputs and
outputs (D-013, see [[2.5 Lua control layer]] §2.5.9).

The engine determines resource locations, staging locations, transaction paths,
and generated file handling. Resource identity is based on manifests, not paths.

### 2.6.14 Streams and I/O

Lua owns user-facing input and output: stdin, stdout, stderr, command streams,
and interactive prompts.

The engine SHOULD provide structured information — diagnostics, logging, progress
events, execution status — rather than writing to user interfaces. Presentation
belongs to Lua or the embedding application.

### 2.6.15 Versioning and compatibility

The boundary MUST expose an API version and the set of supported capabilities.
Lua workflows MAY query them and MAY declare a required version.

Changes breaking existing workflows are compatibility changes and MUST be
documented with a migration path.

### 2.6.16 Boundary invariants

- Lua controls workflow; the engine controls capabilities.
- No direct access to internal state.
- Explicit ownership and lifetime.
- Stable data contracts.
- Structured results and structured errors.
- Resource identity independent of paths.
- Deterministic behaviour.
- Support for CLI, embedded, and automated use.
